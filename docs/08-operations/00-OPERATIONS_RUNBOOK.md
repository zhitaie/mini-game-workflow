# API 服务运行手册

## 1. 适用范围

本手册覆盖当前 `services/api-server` 的 Docker 部署和 SQLite 开发/小规模运行模式。它不把 SQLite 描述成多实例生产数据库方案；MySQL 8 生产适配仍在路线图中。

## 2. 部署前检查

1. 确认 HTTPS 反向代理已将业务域名转发到 API 服务端口。
2. 在微信小游戏后台登记该 HTTPS 请求域名。
3. 仅在部署平台保存 API 密钥、管理员密码和 SSH 私钥。
4. 确认 `API_DB_FILE` 位于持久化卷，例如 `/data/mini-game-workflow.sqlite`。
5. 在变更前保留当前镜像摘要、当前环境变量版本和数据库备份。

部署工作流只在所需 Repository Variables 存在时运行。公开 fork 缺少这些变量时会跳过部署，这是预期行为。

## 3. 发布后验证

1. 请求 `GET /health`，确认服务与数据库路径正常。
2. 用测试账号完成一次登录、拉取配置、读写存档。
3. 在管理端确认新埋点或奖励日志可查询。
4. 微信真机版本还应确认请求域名白名单、登录和广告回调。

## 4. SQLite 备份与恢复

当前最稳妥的文件级备份方式是短暂停止单实例 API，再复制数据库文件：

1. 停止 API 容器。
2. 将持久化数据目录中的 SQLite 文件复制到受访问控制的备份位置，并记录时间和部署版本。
3. 启动 API 容器，执行健康检查。
4. 定期在另一台受控存储上验证可恢复性。

恢复流程：停止 API、保存当前损坏文件副本、写回已验证的备份、确认文件权限、启动 API、执行健康检查和最小登录/存档验证。

不要在服务运行期间直接覆盖 SQLite 文件，也不要将数据库文件提交到 Git。

## 5. 故障处理与回滚

- 健康检查失败：先查看容器状态和最近日志，再检查端口、环境变量和数据库卷挂载。
- 微信请求失败：检查 HTTPS 证书、请求域名白名单、客户端本地 API 配置和服务健康检查。
- 管理端无法登录：确认生产密钥和初始管理员密码已设置；不要回退到开发默认密码。
- 数据异常：停止写入，先备份现场，再恢复到已验证备份或执行经过审查的迁移。

当前部署镜像以 `latest` 为主，尚未提供自动化一键回滚。每次生产变更都应记录镜像摘要；引入 MySQL 适配时应同时增加带版本号的镜像和迁移回滚策略。
