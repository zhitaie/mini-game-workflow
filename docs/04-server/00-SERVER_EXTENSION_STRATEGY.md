# 服务端扩展策略

## 1. 目标

平台应优先采用“一套共用服务端，按 `gameKey` 扩展”的模式。

它要解决的问题是：

- 多个游戏不重复建设登录、存档、配置、公告、埋点等基础能力
- 新增游戏时，不需要复制一整套 server
- 某个游戏需要专属逻辑时，也不至于把共用服务端污染成不可维护的大杂烩

## 2. 总体原则

### 2.1 单体优先

首期使用单体服务端。

原因：

- 对个人开发者维护成本更低
- 本项目当前主要问题不是吞吐，而是复用和边界
- 微服务会过早放大部署、调试、发布复杂度

### 2.2 基础能力共用

下面这些模块默认应是共用的：

- auth
- user
- save
- config
- notice
- analytics
- ad
- reward

这些模块都必须按 `gameKey` 做隔离，而不是默认只有一个游戏。

### 2.3 用户身份模型

当前平台采用下面的身份定义：

- 同一个平台用户，在不同游戏中是不同的游戏用户记录

也就是说：

- `gameA` 中的用户记录与 `gameB` 中的用户记录彼此独立
- 即使它们来自同一个平台 `openId`，也不应默认共用同一条游戏用户数据

首期建议优先采用简单模型：

- `game_user`
  唯一键：`platform + platform_open_id + game_key`

如果未来确实需要跨游戏统一身份，再额外引入全局身份表，但不应倒过来先做重模型

### 2.4 游戏专属逻辑以内聚模块形式扩展

如果某个游戏需要额外后端逻辑，例如：

- PVP 匹配
- 房间系统
- 特殊结算
- 特殊排行榜

它应作为 `api-server` 内部模块存在，而不是另起一整套服务端。

## 3. 推荐目录结构

```text
services/api-server/
├─ src/
│  ├─ app.ts
│  ├─ common/
│  ├─ config/
│  ├─ modules/
│  │  ├─ auth/
│  │  ├─ user/
│  │  ├─ save/
│  │  ├─ config/
│  │  ├─ notice/
│  │  ├─ ad/
│  │  ├─ reward/
│  │  ├─ analytics/
│  │  ├─ game-sim-business/
│  │  └─ game-archery-pvp/
│  └─ types/
```

这里的关键不是“目录长什么样”，而是：

- 基础模块和游戏专属模块分开
- 游戏专属模块仍然跑在同一个服务端里

## 4. `gameKey` 在服务端中的角色

服务端里的绝大多数共享能力都必须显式接收或解析 `gameKey`。

`gameKey` 至少应参与：

- 配置读取
- 存档隔离
- 公告读取
- 埋点归属
- 管理后台筛选

建议规则：

- 请求入口就解析 `gameKey`
- 缺失 `gameKey` 的接口要么拒绝，要么只能访问全局公共资源
- 不允许在深层模块里“猜测当前游戏是谁”
- token、日志、存档、后台筛选都应能还原当前 `gameKey`

## 5. 登录与用户记录建议

更符合当前平台目标的流程是：

1. 客户端携带 `platform`、平台登录凭证和 `gameKey` 发起登录
2. 服务端按 `platform + platform_open_id + gameKey` 查找或创建 `game_user`
3. 签发的 token 中包含 `gameKey` 和 `gameUserId`

这条规则的作用是：

- 从认证入口开始就把游戏边界固定下来
- 避免一个 token 在不同游戏间混用
- 让后续 `save / config / analytics / admin` 都围绕明确的游戏用户展开

## 6. 基础模块与游戏专属模块的边界

### 6.1 基础模块职责

基础模块负责：

- 通用认证
- 通用用户体系
- 通用配置服务
- 通用存档容器
- 通用公告和埋点接收
- 通用广告校验链路
- 通用资产型奖励发放

基础模块不负责：

- 某款游戏专属结算规则
- 某款游戏专属匹配逻辑
- 某款游戏专属经济计算

这里需要额外明确一条：

- 共用 `reward` 模块只处理“可落到通用资产表的数值型奖励”

如果某个奖励会直接改变某款游戏的专属玩法状态，例如：

- 复活
- 解锁某个剧情节点
- 发放复杂背包道具

它应进入该游戏自己的服务端模块，而不是挤进共用 `reward`。

### 6.2 游戏专属模块职责

游戏专属模块只负责：

- 该游戏特有的服务端行为
- 该游戏的特有接口
- 该游戏对共用模块的组合使用

它不应该反向改写共用模块的核心语义。

## 7. 推荐扩展方式

更合理的扩展路径是：

1. 先判断需求是否真的是跨游戏复用。
2. 如果不是，就先放到游戏专属模块。
3. 等被第二款游戏复用后，再考虑上升为共用模块。

这样可以减少“假通用”。

## 8. 数据隔离要求

即使共用服务端，也必须保证：

- 不同游戏的配置数据分区明确
- 不同游戏的存档数据分区明确
- 不同游戏的埋点和日志可筛选
- 后台查询时能按 `gameKey` 精确定位

可以采用的方式包括：

- 表中显式带 `game_key`
- 配置与日志按命名空间组织
- 存档 envelope 内包含 `gameKey`
- token 声明中包含 `gameKey`

关键是隔离规则必须统一。

## 9. 必须避免的错误设计

- 每新增一个游戏就复制一份 `api-server`
- 在共用模块里写死第一款游戏的业务字段
- 游戏专属模块直接依赖另一个游戏的内部逻辑
- 没有 `gameKey` 就默认访问某个游戏的数据
- 后台和服务端对 `gameKey` 的定义不一致
- 把两个游戏的用户记录错误地合并成同一条游戏用户数据

## 10. 何时才考虑拆独立服务

只有在下面这些条件被真实证明存在时，才考虑把某个游戏拆成独立服务：

- 实时对战逻辑复杂到明显压垮共用服务端
- 部署频率和发布节奏与共用服务端强烈冲突
- 团队规模已经不再是单人维护模式

在那之前，优先守住共用单体服务端。
