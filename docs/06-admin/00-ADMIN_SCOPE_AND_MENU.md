# 后台范围与菜单规范

## 1. 目标

后台不是为了做大而全的平台中台，而是为了支撑你独立运营多个小游戏。

它的首期目标是：

- 按 `gameKey` 管理不同游戏
- 查询用户与核心日志
- 管理远程配置
- 管理公告
- 查看广告与奖励链路

## 2. 后台的边界

后台应负责：

- 运营配置管理
- 公告管理
- 用户查询
- 广告与奖励日志查询
- 基础数据筛选与定位

后台不应负责：

- 直接覆盖 `game.config.ts`
- 执行复杂脚本逻辑
- 绕开服务端业务规则直接写数据库

## 3. `gameKey` 视角

后台的第一层隔离维度必须是 `gameKey`。

这意味着：

- 页面默认都需要选定当前游戏
- 同一个管理员查看不同游戏时，数据要明确切换
- 不允许后台页面默认混查所有游戏数据后再靠人工区分

## 4. 推荐首期菜单

建议首期菜单控制在下面这些：

1. 仪表盘
2. 用户查询
3. 配置管理
4. 公告管理
5. 广告日志
6. 奖励日志
7. 埋点查询

## 5. 菜单说明

### 5.1 仪表盘

首期只放轻量指标：

- 新增用户
- 登录用户
- 广告校验次数
- 奖励发放次数
- 埋点上报次数

### 5.2 用户查询

用于按 `gameKey`、平台身份、用户状态查询 `game_user`。

### 5.3 配置管理

只管理远程配置，不管理接入声明。

并且必须区分：

- `draft`
- `active`
- `archived`

### 5.4 公告管理

管理按 `gameKey` 生效的公告与弹窗。

### 5.5 广告日志

查询 `ad_log`，重点看：

- 是否校验通过
- 是否完整观看
- 哪些场景失败多

### 5.6 奖励日志

查询 `reward_log`，重点看：

- 是否命中幂等
- 某个 `bizId` 是否已发奖
- 某用户最近的奖励发放情况
- 奖励后的 `balance_after`

### 5.7 埋点查询

首期可以先做轻量筛选查询，不急着做重图表。

## 6. 菜单设计原则

- 每个页面都要知道当前 `gameKey`
- 页面能力先强调“查得清楚”，再强调“功能很多”
- 任何涉及写操作的页面都要经过服务端接口，而不是前端直接改库

## 7. 必须避免的错误设计

- 配置页里直接编辑 `game.config.ts` 的内容
- 一个页面同时混查多个游戏但没有清晰隔离
- 把奖励发放做成前端直接改表
- 后台展示的字段名与接口、数据库命名完全不一致
