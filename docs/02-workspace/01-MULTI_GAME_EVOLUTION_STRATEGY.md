# 多游戏演进策略

## 1. 先回答最关键的问题

后续新增模块时，是否可能回头修改旧游戏？

答案是：可能，但不应该成为常态。

平台如果设计正确，后续变化应尽量落在下面三类位置：

- 新增共享模块
- 新增服务端模块
- 新增游戏自己的接入代码

而不应该频繁落在：

- 旧游戏已有玩法代码
- 旧游戏已有资源结构
- 旧游戏已经稳定运行的配置和存档协议

## 2. 允许发生的改动

下面这些改动是正常的：

- 共享层新增一个可选模块
- `game.config.ts` 增加一个新开关
- 服务端新增一个按 `gameKey` 生效的接口或模块
- 后台新增一个按 `gameKey` 控制的新配置页
- 存档迁移函数增加新版本迁移逻辑

这些改动的共同特点是：

- 是增量的
- 是可选的
- 默认不破坏旧游戏

## 3. 需要警惕的改动

下面这些改动说明平台边界已经出问题：

- 新增第二个游戏时，必须回头改第一款游戏大量玩法代码。
- 共享层每加一个能力，就要同步修改所有游戏入口。
- 新增一个货币类型，就要重写 `SaveManager` 或重做旧存档。
- 后台每支持一个新游戏，就得复制一份页面。
- 为了第二个游戏的需求，把第一款游戏专属逻辑抽进共享层。

一旦出现这些情况，说明平台并不稳定。

## 4. 控制返工的核心策略

### 4.1 可选模块注册

新模块应通过注册或声明启用，而不是默认全局生效。

示意：

```ts
export default {
  gameKey: 'sim_business',
  features: {
    ads: true,
    analytics: true,
    signIn: false,
    rank: false,
  },
};
```

### 4.2 接口兼容优先

共享层新增参数时优先做可选参数。

不要因为第二个游戏需要一个字段，就直接重写第一版接口。

### 4.3 schema 迁移

存档和配置升级必须通过迁移完成。

示意：

```ts
type SaveMigration = (oldData: unknown) => unknown;
```

平台必须允许：

- 老存档继续读取
- 缺失字段自动补默认值
- 新游戏定义自己的 schema

### 4.4 新能力先在新游戏验证

某个能力是否进入共享层，先在一个具体游戏中验证，再决定是否上升为公共能力。

不要只凭“感觉以后可能会用”就进入 `packages/`。

## 5. 平台完善的真正标准

平台是否完善，不看模块数量，看下面这些事能不能成立：

- 新游戏可以按固定步骤接入。
- 旧游戏不会因为共享层升级被无意破坏。
- 新模块可以可选接入，而不是强迫全量改造。
- 存档、配置、接口都有版本与兼容策略。
- 后台和服务端按 `gameKey` 做隔离管理。

## 6. 当前建议的实施顺序

如果你的优先目标是平台稳定，而不是快速出第一款游戏，那么更合理的顺序是：

1. 先确定仓库结构与分层边界。
2. 先确定 `gameKey`、配置、存档、构建隔离机制。
3. 先确定共享模块的最小稳定接口。
4. 再实现共享模块的第一版。
5. 再接入第一款验证游戏。

这样做的好处是：

- 后续扩展更稳
- 文档和实现一致
- 第一款游戏不会过早污染平台内核
