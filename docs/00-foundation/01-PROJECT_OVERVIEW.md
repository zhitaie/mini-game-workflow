# 项目总览

## 1. 项目目标

本项目要做的不是“通用游戏引擎”，而是一个适合个人开发者长期维护的小游戏平台底座。

它要解决的问题是：

- 每做一个新小游戏，都重复搭登录、广告、存档、配置、埋点、后台、发布流程。
- 第一款游戏做完后，第二款游戏很难复用前面的基础设施。
- 一旦共享层设计不稳，后面新增模块会反向污染旧游戏。

本项目的核心目标是：

- 建立稳定的多游戏共享底座。
- 让第二款、第三款游戏不再从零搭基础设施。
- 把新增模块对旧游戏的影响控制在最小范围。
- 让平台可以长期演进，而不是随着第一款游戏一起固化。

## 2. 当前优先级

当前优先级不是“最快做出第一个游戏”，而是先把平台内核设计稳。

这里的“设计稳”指的是：

- 共享层与游戏层边界清晰。
- 平台支持按游戏隔离配置、存档、构建与发布。
- 平台支持后续新增可选模块。
- 平台支持版本、迁移、兼容，而不是每次改 schema 都推翻旧代码。

## 3. 平台首期边界

首期只做会反复复用、且必须由平台统一承担的能力：

- monorepo 基础结构
- 游戏注册与 `gameKey` 机制
- 客户端共享核心能力
- 共用服务端
- 共用后台
- 多游戏构建与发布边界
- 配置、存档、接口的版本与兼容机制

首期不追求一次写完所有业务模块：

- 任务
- 签到
- 活动
- 邮件
- 排行榜高级玩法
- AB 测试
- 复杂运营体系

这些能力可以后加，但前提是平台内核要允许它们后加。

## 4. 首期成功标准

首期如果满足下面这些条件，就算方向正确：

- 新建一个游戏时，不需要复制旧游戏代码。
- 共享层修改后，不会默认影响所有旧游戏行为。
- 新增一个可选模块时，旧游戏可以选择不接入。
- 存档和配置能够增量扩展，不需要推翻原有结构。
- 构建和发布按游戏独立执行，不会互相污染。

## 5. 风险提醒

这个项目最容易失败的方式不是“模块不够多”，而是：

- 把第一款游戏的玩法假设写进共享层。
- 为了所谓通用，把共享层抽象得过早、过重。
- 没有版本、迁移、兼容策略。
- 后台和服务端按第一款游戏字段写死。
- 共享包逐渐变成“所有游戏杂糅在一起的大仓库”。
