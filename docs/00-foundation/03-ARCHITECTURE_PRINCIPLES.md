# 架构原则

## 1. 总原则

本项目采用“稳定内核优先”策略。

含义不是一开始把所有模块都做完，而是：

- 先设计稳定边界。
- 先定义扩展点。
- 先定义兼容策略。
- 再逐步往里填模块。

## 2. 哪些必须一次设计到位

下面这些部分如果前期不设计清楚，后期大概率会反复回改旧游戏：

### 2.1 仓库分层

- `apps/`：每个具体游戏自己的客户端入口与玩法代码。
- `packages/`：共享包，只放跨游戏复用能力。
- `services/`：共用服务端与后台。

### 2.2 游戏隔离机制

- 每个游戏必须有唯一 `gameKey`。
- 配置、存档、埋点、后台管理、构建发布都必须按 `gameKey` 隔离。
- 平台不能默认把“当前只有一个游戏”写进设计里。
- 同一个平台用户在不同游戏中应视为不同的游戏用户记录。

### 2.3 模块边界

- `AdManager` 负责广告展示与广告结果，不直接决定业务奖励。
- `SaveManager` 负责存取、schema、版本、迁移，不负责具体资源字段定义。
- `ConfigManager` 负责加载、缓存、合并、版本，不负责解释具体业务规则。
- `AnalyticsManager` 负责采集与上报，不负责具体数据分析结论。
- 共享层只负责能力，不负责具体玩法流程。

### 2.4 兼容策略

- 共享接口优先增量扩展，避免破坏性修改。
- 需要破坏性修改时，必须通过版本升级处理，不直接替换旧行为。
- 旧游戏默认不因共享层升级而被动启用新能力。
- 接入声明与运行时配置必须分层，避免同一个字段出现双重真相源。

### 2.5 存档与配置版本机制

- 存档必须有 `schemaVersion`。
- 配置必须有 `configVersion`。
- 升级路径必须允许迁移函数存在。
- 默认值与缺省字段必须可控。

## 3. 哪些可以后补

下面这些能力可以建立在稳定内核上逐步增加：

- 任务系统
- 签到系统
- 邮件系统
- 活动系统
- 高级排行榜
- AB 测试
- 灰度发布
- 高级数据看板

原则是：

- 后补模块应作为“可选能力”接入。
- 新游戏可以启用，旧游戏可以不启用。
- 后补模块不应强迫修改旧游戏玩法代码。

## 4. 共享层禁止事项

共享层禁止出现下面这些情况：

- 写死第一款游戏的资源字段。
- 写死某一款游戏的结算流程。
- 写死某一类游戏的经济模型。
- 把游戏专属 UI、场景、状态机塞进共享包。
- 为了所谓通用，提前引入插件系统、事件总线滥用、复杂中台。

## 5. 平台演进原则

平台后续演进应遵循：

1. 先新增，不先改旧。
2. 先做适配层，不先改业务层。
3. 先局部接入新游戏验证，再推广到共享层。
4. 先兼容旧游戏，再考虑清理历史方案。

## 6. 最重要的判断标准

一个模块是否适合进入共享层，不看它“是否优雅”，而看它是否同时满足：

- 至少会被两款以上游戏重复使用。
- 边界清晰，不依赖某个具体玩法。
- 接口能稳定存在，不会跟着某款游戏频繁变化。
- 抽出来后，能减少未来重复劳动，而不是制造新的耦合。
