# 实施路线图

## 1. 目标

这份文档回答的问题不是“平台要有哪些模块”，而是：

- 实际开始写代码时，先做什么
- 哪些链路必须先跑通
- 哪些内容可以后置

目标是把前面的规范收敛成一条真正可执行的实现路径。

## 2. 实施总原则

整个实施顺序必须遵守：

- 先做稳定边界，再做业务细节
- 先跑通最小闭环，再加更多模块
- 先实现协议一致，再追求功能丰富

## 3. Phase 1：底座与协议落地

目标：

- 把共享层、服务端、后台的最小骨架搭起来
- 让文档中的关键协议在代码里有一一对应的实现位置

### 3.1 工作区结构

先建目录：

- `apps/`
- `packages/`
- `services/`
- `scripts/`
- `sql/`

### 3.2 共享客户端核心包

首期只实现这些：

- `PlatformAdapter`
- `NetworkManager`
- `ConfigManager`
- `SaveManager`
- `AnalyticsManager`
- `AdManager`

暂时不急着做：

- 任务
- 签到
- 排行榜
- 活动

### 3.3 共用服务端

首期只做这些模块：

- `auth`
- `config`
- `save`
- `notice`
- `ad`
- `reward`
- `analytics`

### 3.4 后台首期页面

只做：

- 仪表盘
- 用户查询
- 配置管理
- 公告管理
- 广告日志
- 奖励日志
- 埋点查询

## 4. Phase 2：最小闭环联调

目标：

把下面这条链路跑通：

1. 游戏启动
2. 加载 `game.config.ts`
3. 平台登录
4. 获取 token
5. 拉远程配置
6. 初始化存档
7. 上报基础启动埋点
8. 展示激励广告
9. 调服务端广告校验
10. 调服务端奖励发放
11. 写本地状态并刷新 UI

如果这条链路能稳定跑通，平台基础闭环就成立了。

## 5. Phase 3：第一款验证游戏接入

目标：

- 用一款真实小游戏验证平台是否真的可用

要求：

- 第一款游戏尽量不要选最复杂的实时对战类型
- 重点验证接入成本、配置隔离、存档演进、广告奖励链路

这一阶段最重要的不是做出最多内容，而是识别：

- 哪些抽象是真的稳定
- 哪些抽象还是假通用

## 6. 推荐代码落地顺序

建议实际编码顺序如下：

### 6.1 先建表和基础服务

先根据 SQL 草案创建：

- `game_user`
- `user_save`
- `game_config`
- `notice`
- `ad_log`
- `user_asset_balance`
- `reward_log`
- `analytics_event`

### 6.2 先写登录与配置

因为后续绝大多数模块都依赖：

- `gameKey`
- token
- 远程配置
- 统一网络请求

### 6.3 再写存档

因为存档要和登录身份、`game_user`、`schemaVersion` 对齐。

### 6.4 再写埋点接收与查询

顺序建议：

1. `AnalyticsManager`
2. `/api/analytics/events`
3. `analytics_event`
4. 后台埋点查询页

### 6.5 再写广告与奖励链路

顺序建议：

1. `PlatformAdapter.ad`
2. `AdManager`
3. `/api/ad/verify`
4. `user_asset_balance`
5. `/api/reward/claim`
6. `ad_log` / `reward_log`

### 6.6 最后接后台

后台应该建立在：

- 接口已定
- 表结构已定
- 字段命名已定

的基础上，而不是反过来推动后端设计。

## 7. 每个阶段的验收标准

### 7.1 Phase 1 验收

- 目录结构已建立
- 文档对应的模块位置清楚
- 数据库表已创建
- 基础服务能启动

### 7.2 Phase 2 验收

- 登录成功
- token 正确绑定 `gameKey`
- 配置可拉取且版本可识别
- 存档可读写
- 埋点可入库且能按 `gameKey` 查询
- 广告校验和奖励发放能串通

### 7.3 Phase 3 验收

- 一款真实游戏成功接入
- 不需要改动平台根边界
- 后台可以查到用户、配置、广告日志、奖励日志、埋点

## 8. 当前明确后置的内容

下面这些明确不进入首期必做范围：

- 完整任务系统
- 完整签到系统
- 高级排行榜
- 活动系统
- 邮件系统
- 灰度和 AB 测试
- 重型数据看板

## 9. 当前最重要的判断标准

后续是否继续往下堆模块，不看“还能不能再加功能”，而看：

- 新模块是否会破坏已有边界
- 新游戏接入时是否还要回头改旧游戏
- 当前抽象是否已经在真实项目中验证过

如果这三点不成立，就不应该继续扩范围。
